# Module 04 - Terraform State Management

Terraform state is the memory of your infrastructure. It maps the resources in
your configuration to real objects in AWS, stores computed attributes returned by
providers, and lets Terraform decide what must be created, updated, replaced, or
destroyed during the next plan.

This module teaches the state skills expected from production Terraform
engineers: reading state safely, moving resources without replacement, locking
state, migrating from local to remote backends, importing existing AWS resources,
recovering from corruption, and detecting drift.

## Learning objectives

By the end of this module you will be able to:

- Explain what `terraform.tfstate` contains and why it must be protected.
- Configure an S3 backend with DynamoDB locking.
- Migrate local state to remote state without recreating resources.
- Use state commands such as `list`, `show`, `pull`, `mv`, `rm`, and `replace-provider`.
- Import existing AWS resources into Terraform management.
- Recover from common state failures using backups, versioned S3 objects, and
  deliberate state surgery.
- Detect and respond to drift in production environments.

## 1. What is `terraform.tfstate`?

Terraform compares three things:

1. Configuration: the `.tf` files you write.
2. State: Terraform's last known mapping of configuration to real resources.
3. Remote infrastructure: what the provider reads from AWS during refresh.

The state file is commonly named `terraform.tfstate` when using the default local
backend. It is JSON, but it is not meant to be edited by hand during normal
operations.

Important contents include:

- Terraform version and state format version.
- Resource addresses such as `aws_s3_bucket.logs`.
- Provider addresses such as `registry.terraform.io/hashicorp/aws`.
- Resource IDs such as an S3 bucket name, VPC ID, or IAM role name.
- Attributes returned by providers, including computed values like ARNs.
- Dependency metadata used to order operations.
- Sensitive values, often in plain text, even when marked `sensitive` in output.

Example resource address:

```text
module.network.aws_vpc.this
module.network.aws_subnet.private[0]
aws_iam_role.ecs_task_execution
```

Example simplified state shape:

```json
{
  "version": 4,
  "terraform_version": "1.8.0",
  "serial": 12,
  "lineage": "3f7e2f84-bb52-46f1-a23f-0ef3c1b4d6a2",
  "outputs": {
    "vpc_id": {
      "value": "vpc-0123456789abcdef0",
      "type": "string"
    }
  },
  "resources": [
    {
      "mode": "managed",
      "type": "aws_vpc",
      "name": "main",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [
        {
          "attributes": {
            "id": "vpc-0123456789abcdef0",
            "cidr_block": "10.0.0.0/16"
          }
        }
      ]
    }
  ]
}
```

### Why state is sensitive

State can contain:

- RDS passwords generated by `random_password`.
- Secrets passed into resources.
- IAM policy documents.
- ARNs, account IDs, and network topology.
- Private endpoint DNS names.

Production rule: treat state like a secret. Store it remotely with encryption,
least-privilege IAM, versioning, and audit logs.

## 2. State internals

### Resource addresses

Terraform resource addresses identify an object in state. Common forms:

```text
aws_instance.web
aws_instance.web[0]
aws_instance.web["blue"]
module.vpc.aws_subnet.private[1]
module.service.module.task.aws_iam_role.this
```

Addresses change when you:

- Rename a resource block.
- Move a resource into or out of a module.
- Change `count` to `for_each`.
- Change a `for_each` key.

When the address changes but the real resource should remain the same, use
`terraform state mv` or a `moved` block.

### Lineage and serial

State has a `lineage` and a `serial`.

- `lineage` identifies a state history.
- `serial` increments every time the state changes.

Backends use this information to reject unsafe writes. If you accidentally try
to push older state over newer state, Terraform can detect that the serial is
stale.

### Refresh behavior

During `terraform plan`, Terraform usually refreshes state by calling provider
read APIs. A refresh updates state with current remote values before computing
the diff.

Useful commands:

```bash
terraform plan
terraform plan -refresh=false
terraform apply -refresh=false
terraform refresh
```

Use `-refresh=false` carefully. It can be useful during provider outages or
large emergency changes, but it hides drift.

## 3. Local state vs remote state

Local state is acceptable for early learning, but it is not production-ready.

| Concern | Local state | Remote state |
| --- | --- | --- |
| Collaboration | Unsafe | Shared |
| Locking | None by default | Backend dependent |
| Backups | Manual | Versioning/snapshots possible |
| Secrets protection | Local disk | IAM + encryption |
| Auditability | Weak | CloudTrail/backend logs |

Production teams almost always use a remote backend such as:

- S3 with DynamoDB locking for AWS-centric teams.
- Terraform Cloud / HCP Terraform.
- Consul for specialized internal platforms.
- Azure Storage or Google Cloud Storage for non-AWS environments.

## 4. Remote backend with S3 and DynamoDB

The most common AWS backend uses:

- S3 bucket: stores the state object.
- DynamoDB table: stores a lock record during state-changing operations.
- KMS/SSE: encrypts state at rest.
- Bucket versioning: enables rollback to previous state objects.
- IAM policies: restrict access to state paths.

### Locking flow

```text
Developer / CI
     |
     | terraform apply
     v
+------------------+        PutItem if no lock exists        +----------------------+
| Terraform client | ---------------------------------------> | DynamoDB lock table  |
+------------------+                                         +----------------------+
     |                                                              |
     | lock acquired                                                |
     v                                                              |
+------------------+        GetObject / PutObject             +----------------------+
| Terraform client | ---------------------------------------> | S3 state bucket      |
+------------------+                                         +----------------------+
     |
     | DeleteItem when complete
     v
+------------------+
| Lock released    |
+------------------+
```

When a second operator runs `terraform apply`, it tries to write the same lock
record. DynamoDB conditional writes prevent that second operation from
continuing.

```text
Operator A: acquire lock -> apply in progress
Operator B: acquire lock -> ConditionalCheckFailedException -> wait or fail
```

### Backend configuration

Backends are configured in a `terraform` block:

```hcl
terraform {
  backend "s3" {
    bucket         = "my-company-prod-terraform-state"
    key            = "platform/prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "my-company-prod-terraform-locks"
    encrypt        = true
  }
}
```

For reusable projects, prefer partial backend configuration:

```hcl
terraform {
  backend "s3" {}
}
```

Then initialize with environment-specific values:

```bash
terraform init \
  -backend-config="bucket=my-company-prod-terraform-state" \
  -backend-config="key=platform/prod/terraform.tfstate" \
  -backend-config="region=us-east-1" \
  -backend-config="dynamodb_table=my-company-prod-terraform-locks" \
  -backend-config="encrypt=true"
```

Partial configuration keeps environment-specific backend names out of reusable
module examples and avoids committing local test bucket names.

## 5. Bootstrapping the backend

Terraform cannot store state in an S3 bucket until the bucket exists. This
creates a chicken-and-egg problem.

Common production solution:

1. Use a small `bootstrap` Terraform project with local state.
2. Create the S3 bucket and DynamoDB lock table.
3. Enable bucket versioning, encryption, and public access block.
4. Configure the application project to use the S3 backend.
5. Run `terraform init -migrate-state` in the application project.
6. Store the bootstrap state securely or move it into a separate remote backend.

```text
bootstrap/ local state
   |
   | creates
   v
S3 state bucket + DynamoDB lock table
   |
   | used by
   v
app/ remote backend
```

## 6. Migrating state

### Local to remote migration

After adding backend configuration:

```bash
terraform init -migrate-state
```

Terraform will ask whether to copy existing local state to the new backend.
Answer `yes` after confirming the backend points to the correct bucket, key, and
account.

For non-interactive CI:

```bash
terraform init -migrate-state -input=false \
  -backend-config="bucket=my-company-dev-terraform-state" \
  -backend-config="key=app/dev/terraform.tfstate" \
  -backend-config="region=us-east-1" \
  -backend-config="dynamodb_table=my-company-dev-terraform-locks" \
  -backend-config="encrypt=true"
```

### Changing backend configuration

When backend settings change:

```bash
terraform init -reconfigure
```

Use `-reconfigure` when you intentionally want Terraform to forget previous
backend settings and use the current config. Use `-migrate-state` when you want
Terraform to copy state from one backend location to another.

### Workspace state paths

Terraform workspaces can create multiple state files. With S3:

```hcl
terraform {
  backend "s3" {
    bucket               = "my-company-terraform-state"
    key                  = "app/terraform.tfstate"
    workspace_key_prefix = "workspaces"
    region               = "us-east-1"
    dynamodb_table       = "my-company-terraform-locks"
    encrypt              = true
  }
}
```

The default workspace uses `app/terraform.tfstate`; other workspaces use paths
under `workspaces/<workspace>/app/terraform.tfstate`.

Production note: many teams prefer separate directories or separate backend keys
over Terraform workspaces because the environment boundary is more explicit.

## 7. State locking

Locking prevents two writers from modifying state at the same time. Without
locking, two applies can both read the same starting state, make different AWS
changes, and write conflicting final state.

Commands that usually acquire a lock:

```bash
terraform apply
terraform destroy
terraform import
terraform state mv
terraform state rm
terraform state push
```

Lock timeout example:

```bash
terraform apply -lock-timeout=10m
```

Disable locking only for exceptional recovery actions:

```bash
terraform plan -lock=false
```

Never use `-lock=false` for normal production applies.

### Force unlocking

If a Terraform process crashes, the lock can remain. Terraform will show a lock
ID:

```text
Error acquiring the state lock
Lock Info:
  ID:        12345678-1234-1234-1234-123456789abc
  Operation: OperationTypeApply
  Who:       ci@runner
```

Only after confirming no apply is running:

```bash
terraform force-unlock 12345678-1234-1234-1234-123456789abc
```

Production checklist before force unlock:

- Check CI for running jobs.
- Ask the operator who owns the lock.
- Inspect CloudTrail or DynamoDB item timestamps if needed.
- Confirm no AWS changes are still in progress.

## 8. State commands every engineer must know

### List resources

```bash
terraform state list
terraform state list 'module.vpc.*'
```

### Show one resource

```bash
terraform state show aws_s3_bucket.logs
terraform state show 'module.vpc.aws_subnet.private[0]'
```

### Pull state for inspection

```bash
terraform state pull > state.json
```

Use `pull` for read-only inspection and backup before state surgery. Protect the
downloaded file because it can contain secrets.

### Move a state address

Use `state mv` when configuration addresses change but the underlying AWS object
must remain.

Rename a resource:

```bash
terraform state mv aws_s3_bucket.old_name aws_s3_bucket.logs
```

Move a resource into a module:

```bash
terraform state mv aws_vpc.main module.network.aws_vpc.this
```

Move from `count` to `for_each`:

```bash
terraform state mv 'aws_subnet.private[0]' 'aws_subnet.private["us-east-1a"]'
```

Modern Terraform also supports declarative `moved` blocks:

```hcl
moved {
  from = aws_s3_bucket.old_name
  to   = aws_s3_bucket.logs
}
```

Prefer `moved` blocks for changes committed to a shared repository because every
operator and CI runner sees the migration.

### Remove a resource from state

`state rm` makes Terraform forget a resource. It does not delete the AWS object.

```bash
terraform state rm aws_s3_bucket.legacy_logs
```

Use cases:

- Hand a resource back to manual management.
- Recover when a resource was deleted outside Terraform and you want to recreate
  it with a clean address.
- Split a large state file into smaller projects.

Danger: if the configuration still contains the resource, the next plan will
propose creating it again.

### Replace provider addresses

Provider source addresses can change during migrations:

```bash
terraform state replace-provider \
  registry.terraform.io/-/aws \
  registry.terraform.io/hashicorp/aws
```

Run `terraform plan` immediately after provider replacement.

### Push state

```bash
terraform state push state.json
```

This is a last-resort recovery command. Prefer backend-native version restore or
`terraform import` when possible. If you must push state, take a backup first and
use peer review.

## 9. Importing existing resources

Import connects an existing remote object to a Terraform resource address.

Traditional import:

```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "existing-company-logs-prod"
}
```

```bash
terraform import aws_s3_bucket.logs existing-company-logs-prod
terraform plan
```

Import an IAM role:

```hcl
resource "aws_iam_role" "app" {
  name = "existing-app-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = {
        Service = "ecs-tasks.amazonaws.com"
      }
      Action = "sts:AssumeRole"
    }]
  })
}
```

```bash
terraform import aws_iam_role.app existing-app-role
```

Import a subnet:

```bash
terraform import 'module.network.aws_subnet.private["us-east-1a"]' subnet-0123456789abcdef0
```

### Declarative import blocks

Terraform supports import blocks that can be reviewed in code:

```hcl
import {
  to = aws_s3_bucket.logs
  id = "existing-company-logs-prod"
}

resource "aws_s3_bucket" "logs" {
  bucket = "existing-company-logs-prod"
}
```

Workflow:

```bash
terraform plan
terraform apply
terraform plan
```

After the import is complete and the follow-up plan is clean, remove the import
block or keep it only as long as your team convention allows.

### Import best practices

- Write the resource block before importing.
- Start with the minimum arguments required to represent the existing object.
- Run `terraform plan` after import and reconcile differences.
- Do not blindly accept a plan that replaces an imported production resource.
- Import dependent resources separately, such as S3 bucket versioning, bucket
  policy, and public access block.

Example S3 imports:

```bash
terraform import aws_s3_bucket.logs existing-company-logs-prod
terraform import aws_s3_bucket_versioning.logs existing-company-logs-prod
terraform import aws_s3_bucket_public_access_block.logs existing-company-logs-prod
```

## 10. Remote state data

Remote state outputs can be consumed by another configuration:

```hcl
data "terraform_remote_state" "network" {
  backend = "s3"

  config = {
    bucket         = "my-company-prod-terraform-state"
    key            = "network/prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "my-company-prod-terraform-locks"
  }
}

locals {
  vpc_id = data.terraform_remote_state.network.outputs.vpc_id
}
```

Use this sparingly. Remote state grants access to all outputs and often implies
access to the state object. For stable cross-stack contracts, consider publishing
values to AWS Systems Manager Parameter Store or Secrets Manager instead.

## 11. Drift detection

Drift occurs when real infrastructure no longer matches Terraform configuration
and state. Causes include:

- Manual console changes.
- Emergency CLI changes.
- AWS service-side defaults changing.
- Autoscaling behavior.
- External controllers such as Kubernetes or ECS deployment controllers.

Detect drift:

```bash
terraform plan -detailed-exitcode
```

Exit codes:

- `0`: no changes.
- `1`: error.
- `2`: changes present.

CI drift check example:

```bash
terraform init -input=false
terraform plan -detailed-exitcode -input=false -no-color
```

Production pattern:

```text
Nightly schedule
     |
     v
terraform plan -detailed-exitcode
     |
     +--> exit 0: record healthy
     |
     +--> exit 2: notify platform channel and attach plan
     |
     +--> exit 1: create incident or ticket
```

Drift response:

1. Decide whether the real change should be kept.
2. If yes, update Terraform configuration to match and apply.
3. If no, apply Terraform to restore the declared configuration.
4. If state is wrong but AWS is correct, use import or state commands carefully.

## 12. Recovery and state corruption

State problems are stressful because the infrastructure may be healthy while
Terraform's memory is wrong. Slow down and preserve evidence.

### Recovery checklist

1. Stop all applies.
2. Acquire or inspect the state lock.
3. Pull a copy of current state:

   ```bash
   terraform state pull > current-state.json
   ```

4. Identify the last known good state version.
5. Compare state versions and recent Git commits.
6. Use the least destructive repair:
   - Restore an S3 object version.
   - Use `terraform import`.
   - Use `terraform state mv`.
   - Use `terraform state rm`.
   - Use `terraform state push` only when necessary.
7. Run `terraform plan` and review replacements carefully.
8. Document the incident and add prevention.

### Using S3 versioning for restore

If the backend bucket has versioning:

```bash
aws s3api list-object-versions \
  --bucket my-company-prod-terraform-state \
  --prefix platform/prod/terraform.tfstate
```

Download a previous version:

```bash
aws s3api get-object \
  --bucket my-company-prod-terraform-state \
  --key platform/prod/terraform.tfstate \
  --version-id "3HL4k..." \
  recovered.tfstate
```

Inspect it:

```bash
terraform show -json recovered.tfstate > recovered.json
```

Restore only after review:

```bash
terraform state push recovered.tfstate
```


## 15. Advanced topics

### Splitting state

Large monolithic states slow down plans and increase blast radius. Split state by
ownership and lifecycle:

- `network`: VPC, subnets, shared endpoints.
- `security`: shared IAM roles, KMS keys, guardrails.
- `data`: RDS, DynamoDB, ElastiCache.
- `services`: application services.

Avoid splitting resources that must change atomically.

### State and secrets

Marking an output as sensitive hides CLI display, not state storage:

```hcl
output "db_password" {
  value     = random_password.db.result
  sensitive = true
}
```

The password is still in state. Prefer generating secrets outside Terraform when
the value does not need to be known by Terraform, or write generated values to
Secrets Manager and strictly control state access.

### CI/CD locking

Use one apply pipeline per state file. Multiple plan jobs are fine, but apply
jobs should be serialized. Backend locks are a final safety net, not a queueing
system.

### State in disaster recovery

Back up state in the same way you back up data:

- Enable S3 versioning.
- Enable default encryption.
- Replicate critical state buckets to another region if required by policy.
- Use MFA delete or restricted delete permissions for high-risk accounts.
- Test restore procedures.

### OpenTofu compatibility

State concepts are similar in Terraform and OpenTofu, but backends, provider
metadata, and future state formats can diverge. Do not casually share one state
between different tools without testing and a rollback plan.

## 16. Interview Q&A

### Q1: Why does Terraform need state?

Terraform needs state to map configuration addresses to real resource IDs and to
store provider-returned attributes. Without state, Terraform would not know that
`aws_vpc.main` corresponds to `vpc-1234`, whether a resource was created by this
configuration, or which dependencies exist between resources.

### Q2: Why is local state unsafe for teams?

Local state can be lost, overwritten, or used concurrently by multiple people.
It also lacks central access control, audit logging, locking, and automated
backups. Remote state solves these problems when configured with encryption,
versioning, and locking.

### Q3: How does DynamoDB locking work with the S3 backend?

Terraform writes a lock item into DynamoDB using a conditional write. If no lock
exists, the write succeeds and the operation continues. If another operation
already holds the lock, the conditional write fails and Terraform waits or exits.
When the operation completes, Terraform deletes the lock item.

### Q4: What is the difference between `terraform state rm` and `terraform destroy`?

`terraform state rm` removes an object from Terraform state only. The AWS
resource remains. `terraform destroy` deletes the AWS resource and updates state
after deletion.

### Q5: When should you use `terraform state mv`?

Use it when the Terraform address changes but the same real resource should
continue to be managed. Examples include resource renames, moving resources into
modules, and changing from `count` indexes to `for_each` keys.

### Q6: What is drift?

Drift is a difference between Terraform configuration/state and real
infrastructure. It usually happens through manual changes, emergency fixes, or
external controllers. Drift is detected with `terraform plan` and resolved by
either updating configuration or applying Terraform to restore the desired state.

### Q7: Why should state buckets use versioning?

Versioning provides recovery points. If state is corrupted, accidentally pushed,
or overwritten, you can inspect and restore a previous version instead of
reconstructing state from scratch.

### Q8: Is a sensitive output encrypted in state?

No. `sensitive = true` hides the value from CLI output, but the value is still
stored in state. Encryption depends on the backend storage configuration.

### Q9: How do you import an existing resource?

Write the Terraform resource block, run `terraform import ADDRESS ID` or use an
import block, then run `terraform plan` and adjust configuration until Terraform
does not propose unexpected changes.

### Q10: What should you do before force-unlocking state?

Confirm no Terraform operation is still running, check CI jobs and operator
activity, inspect the lock metadata, and communicate with the team. Force unlock
only removes the lock; it does not resolve partially applied infrastructure
changes.

## 17. Real-world case study: state corruption recovery

### Scenario

A platform team manages production networking with an S3 backend and DynamoDB
locking. During a refactor, an engineer attempts to move subnet resources into a
new `network` module. They run several `terraform state mv` commands locally.
One command uses the wrong destination address:

```bash
terraform state mv aws_subnet.private[1] module.network.aws_subnet.public[1]
```

The next plan proposes replacing a private subnet and modifying route table
associations. The engineer stops before applying, but the incorrect state move
has already been written to remote state.

### Response

The incident lead takes these steps:

1. Stops all network applies in CI.
2. Confirms the DynamoDB lock is released.
3. Pulls current state:

   ```bash
   terraform state pull > bad-network-state.json
   ```

4. Lists S3 object versions for the state key.
5. Downloads the state version from before the incorrect move.
6. Compares resource addresses in both files.
7. Chooses a minimal repair instead of restoring the whole file because only one
   address is wrong:

   ```bash
   terraform state mv \
     'module.network.aws_subnet.public[1]' \
     'module.network.aws_subnet.private[1]'
   ```

8. Runs `terraform plan` and confirms there are no subnet replacements.
9. Opens a follow-up pull request adding declarative `moved` blocks so the
   address migration is repeatable in every environment.
10. Adds a runbook requirement: all future state moves must be tested in a lower
    environment and copied into a reviewed migration checklist.

### Lessons

- State commands are writes. Treat them like production changes.
- S3 versioning gave the team a safe comparison point.
- Stopping before apply prevented real infrastructure damage.
- Declarative `moved` blocks are safer for shared refactors than ad hoc local
  commands.
- A clean plan after recovery is necessary but not enough; document what
  happened and improve the process.
